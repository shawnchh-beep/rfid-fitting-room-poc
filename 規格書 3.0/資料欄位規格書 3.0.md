RFID 試衣間 Demo 資料架構規格書 v1.0

1. 文件目的

本文件用於定義 RFID 試衣間 Demo 系統的核心資料架構，作為後續以下工作的基礎：
	•	前端 UI 開發
	•	模擬資料生成
	•	後端資料模型設計
	•	KPI 計算邏輯
	•	AI 洞察邏輯
	•	API 與資料表設計

本系統的主要展示目標為：
	•	商品進入試衣間後的即時追蹤
	•	試衣 session 建立
	•	停留時間與商品組合分析
	•	離開試衣間後的去向分析
	•	與成交結果的關聯分析
	•	依據 RFID 行為資料產出 AI 建議

⸻

2. 範圍定義

2.1 核心範圍 Included

本版本資料架構包含以下能力：
	•	商品基本資料管理
	•	EPC 與 SKU 對應
	•	門市與區域資料
	•	商品進出試衣間事件
	•	試衣 session 建立與管理
	•	商品離開試衣間後去向追蹤
	•	商品成交結果記錄
	•	KPI 聚合資料
	•	Alert / Insight / Recommendation 資料結構

⸻

2.2 非核心範圍 Excluded from Core Scope

以下內容不列為本版本核心必要能力：
	•	精準偵測商品是否離開貨架
	•	全店 item-level 即時位置追蹤
	•	顧客身份辨識
	•	商品在全店完整移動路徑
	•	完整 POS / ERP 真實串接

若未來需要，可作為擴充模組處理。

⸻

3. 資料架構總覽

整體資料架構建議分為 7 類核心實體：
	1.	Store：門市
	2.	Zone：區域
	3.	Item / SKU：商品與單品
	4.	Session：試衣 session
	5.	Event：商品事件流
	6.	Transaction / Outcome：成交或結果
	7.	Insight Layer：KPI、Alert、AI Insight、Recommendation

⸻

4. 核心實體定義

⸻

4.1 Store

代表一個門市或 demo 場景。

用途
	•	支援多門市
	•	作為資料切分與比較的最上層維度

主要欄位

欄位	型別	說明
store_id	string	門市唯一 ID
store_code	string	門市代碼
store_name	string	門市名稱
store_type	string	門市類型，例如 flagship / outlet / demo
country	string	國家
city	string	城市
timezone	string	時區
status	string	active / inactive
created_at	datetime	建立時間
updated_at	datetime	更新時間


⸻

4.2 Zone

代表門市內部區域。

用途
	•	定義商品目前所在位置
	•	支援 zone-based tracking
	•	作為事件 from/to 的位置來源

建議 zone 類型
	•	entrance
	•	display_area
	•	fitting_room
	•	checkout
	•	backroom
	•	unknown

主要欄位

欄位	型別	說明
zone_id	string	區域唯一 ID
store_id	string	所屬門市
zone_code	string	區域代碼
zone_name	string	區域名稱
zone_type	string	區域類型
fitting_room_id	string/null	若為試衣間，對應試衣間 ID
display_order	int	UI 顯示順序
is_active	boolean	是否啟用
created_at	datetime	建立時間
updated_at	datetime	更新時間


⸻

4.3 FittingRoom

雖然 fitting room 也可視為 zone，但建議獨立一個實體，方便後續做 session 與 dwell 管理。

主要欄位

欄位	型別	說明
fitting_room_id	string	試衣間唯一 ID
store_id	string	所屬門市
zone_id	string	對應 zone
fitting_room_code	string	試衣間代碼
fitting_room_name	string	顯示名稱
capacity	int	建議容量，可為 demo 用
status	string	available / occupied / maintenance
created_at	datetime	建立時間
updated_at	datetime	更新時間


⸻

4.4 ProductStyle

代表商品款式層級資料，不含單一件 item。

用途
	•	商品分析頁主要使用
	•	KPI / pairing / size heatmap 的聚合主體之一

主要欄位

欄位	型別	說明
style_id	string	款式唯一 ID
brand	string	品牌名稱
category	string	類別，例如 dress / jacket / pants
product_name	string	商品名稱

base_price	decimal	建議售價
currency	string	幣別
is_active	boolean	是否有效
created_at	datetime	建立時間
updated_at	datetime	更新時間


⸻

4.5 SKU

代表可售賣 SKU，通常為 style + color + size。

用途
	•	商品分析核心粒度
	•	尺寸與顏色分析主要依據

主要欄位

欄位	型別	說明
sku_id	string	SKU 唯一 ID

代表單一件實體商品，也就是 RFID item-level 追蹤對象。

用途

主要欄位

is_active	boolean	是否有效

建議 current_status 枚舉

5. Session 架構

⸻

5.1 FittingSession

代表一次試衣行為的主體。

設計原則

因為 demo 不追蹤顧客身份，所以 session 是以：
	•	fitting room
	•	時間區段
	•	進入該試衣間的商品群組
來定義

主要欄位

欄位	型別	說明
session_id	string	session 唯一 ID
store_id	string	所屬門市
fitting_room_id	string	所屬試衣間
session_status	string	active / completed / abandoned
started_at	datetime	session 開始時間
ended_at	datetime/null	session 結束時間
dwell_seconds	int/null	總停留秒數
item_count	int	本 session 商品數
converted_item_count	int	成交商品數
returned_item_count	int	回架商品數
moved_to_checkout_count	int	前往 checkout 數
outcome_type	string	converted / non_converted / partial_converted
created_by	string	demo_manual / simulation / integration
created_at	datetime	建立時間
updated_at	datetime	更新時間


⸻

5.2 SessionItem

主要欄位

欄位	型別	說明

sku_id	string	冗餘欄位

exited_at	datetime/null	離開 session 時間
item_dwell_seconds	int/null	商品停留時間

6. Event 架構

這是系統最核心的底層資料。

⸻

6.1 Event

所有商品行為都應以 event 流形式記錄。

設計原則
	•	一個 event 代表一次明確狀態改變或可辨識行為
	•	上層 session、KPI、AI 都由 event 推導
	•	demo 模式與未來真實系統都可共用同一 event schema

主要欄位

欄位	型別	說明
event_id	string	事件唯一 ID
event_type	string	事件類型
event_time	datetime	事件時間
store_id	string	門市
zone_from_id	string/null	前一區域
zone_to_id	string/null	新區域
fitting_room_id	string/null	若與試衣間相關則填入
session_id	string/null	若已歸屬 session 則填入
item_id	string	商品 item ID
epc	string	EPC
sku_id	string	SKU
style_id	string	style
quantity	int	預設 1
source_type	string	simulation / ui_manual / reader / api
source_id	string/null	裝置或模擬來源 ID
confidence_score	decimal/null	信心值，未來擴充用
raw_payload	json/null	原始資料
created_at	datetime	建立時間


⸻

11. 關聯關係總覽

下面是核心關係。

11.1 基本關係
	•	一個 Store 有多個 Zone
	•	一個 Store 有多個 FittingRoom
	•	一個 ProductStyle 有多個 SKU
	•	一個 SKU 有多個 Item
	•	一個 Item 有多個 Event
	•	一個 FittingSession 有多個 SessionItem
	•	一個 SessionItem 對應一個 Item
	•	一個 FittingSession 可對應多個 ItemOutcome
	•	一個 Transaction 有多個 TransactionItem

11.2 分析關係
	•	KPI Snapshot 可由 Event / Session / Outcome 聚合而來
	•	Alert 可由 Event 或 Session 規則觸發
	•	Insight 可由 KPI、Session、Outcome 聚合後產出
	•	Recommendation 可由 Insight 延伸產出

12. 商品狀態流定義

建議本系統使用以下商品主狀態流：
	1.	on_display
	2.	in_fitting_room
	3.	left_fitting_room
	4.	returned_to_floor
	5.	moved_to_checkout
	6.	sold

補充說明
	•	left_fitting_room 可作為中間狀態，也可由事件層表達
	•	returned_to_floor 與 moved_to_checkout 為主要分流結果
	•	sold 為最終轉換結果

13. Session 狀態流定義

建議 session 狀態：
	1.	active
	2.	completed
	3.	abandoned

Session 啟動條件
	•	第一件商品進入某 fitting room 時建立 session

Session 結束條件

符合以下任一條件可結束：
	•	所有商品已離開試衣間
	•	超過指定無活動時間
	•	手動結束
	•	模擬系統自動結束

20. v3.1 增補需求：多語言與登入系統

本章為 3.0 追加需求，後續 UI / API / DB 皆需對齊。

20.1 多語言功能

### 支援語言
- 英文（`en`，系統預設）
- 繁體中文（`zh-Hant`）
- 簡體中文（`zh-Hans`）

### 語言切換規則
1. 優先使用使用者偏好語言（`preferred_locale`）。
2. 若該語言翻譯不存在，回退到預設英文（`en`）。
3. 管理後台可維護各語系文案。

### 需支援多語言的主要欄位
- 商品名稱/描述（Style、SKU）
- 區域顯示名稱（Zone）
- 告警標題/描述（Alert）
- 洞察標題/描述（Insight）
- 建議標題/描述（Recommendation）

### 多語言資料結構建議
- 主表保留英文欄位作為 fallback。
- 另外建立 i18n 明細表，鍵值建議：`(entity_id, locale)`。

範例欄位：

| 欄位 | 型別 | 說明 |
|---|---|---|
| id | string/uuid | 翻譯資料主鍵 |
| entity_type | string | 例如 `style` / `sku` / `alert` |
| entity_id | string/uuid | 對應主表 ID |
| locale | enum | `en` / `zh-Hant` / `zh-Hans` |
| title | string | 顯示標題 |
| description | string/null | 顯示描述 |
| created_at | datetime | 建立時間 |
| updated_at | datetime | 更新時間 |

20.2 登入系統

### 帳號角色
- 管理員（`admin`）
- 店員（`store_clerk`）
- 店經理（`store_manager`）
- 訪客帳號（`guest`）

### 權限概念（摘要）
- `guest`：唯讀 demo 畫面，不可執行資料寫入。
- `store_clerk`：可進行日常營運操作（如事件流程操作）。
- `store_manager`：含店員權限，並可查詢門市 KPI/報表。
- `admin`：全域設定與帳號權限管理。

### 使用者資料結構建議

| 欄位 | 型別 | 說明 |
|---|---|---|
| user_id | string/uuid | 使用者唯一 ID（可對接 Supabase Auth） |
| email | string | 登入帳號 |
| display_name | string | 顯示名稱 |
| role | enum | `admin` / `store_clerk` / `store_manager` / `guest` |
| preferred_locale | enum | `en` / `zh-Hant` / `zh-Hans`，預設 `en` |
| store_scope | string/null | 門市範圍（店員/店經理） |
| is_active | boolean | 帳號是否啟用 |
| last_login_at | datetime/null | 上次登入時間 |
| created_at | datetime | 建立時間 |
| updated_at | datetime | 更新時間 |

20.3 與既有資料架構的整合要求

1. 所有前端頁面與 API 回傳應可接收 `locale` 參數（未提供時預設 `en`）。
2. 事件寫入、交易寫入等動作需有登入身分（至少 `store_clerk` 以上）。
3. 權限拒絕需回傳標準錯誤碼（401/403）與可辨識訊息。
4. 角色與語系需可追蹤（記錄於操作 log / metadata）。
